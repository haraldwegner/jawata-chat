# jawata chat and jawata Java v0.1.0

The first release. Two VS Code extensions, versioned and released together. Each is attached to this release as a `.vsix` file:

- `jawata-chat-0.1.0.vsix`: jawata chat, a chat for ACP (Agent Client Protocol) agents. It starts the one agent named in the `jawataChat.agent` setting (command, args, env) and talks to it over stdio. The chat can be placed in the left side bar, the right side bar, the bottom panel or the editor area (`jawataChat.placement`).
- `jawata-java-0.1.0.vsix`: jawata Java, Java language support from the jawata engine. It starts the launcher named in `jawataJava.server` (the jawata program with `--lsp`), which forwards the editor's messages to the engine that is already running. It starts no language server of its own. If another Java language-server extension (by default `redhat.java`) is installed, it says so.

## Starting the studio

At activation each extension reads the engine's base address from `JAWATA_URL` in the env of its own setting (`jawataChat.agent`, `jawataJava.server`) and sends it an HTTP request. Any HTTP answer, including 401 or 404, counts as the service answering, and then nothing else happens.

If nothing answers, the extension starts the program named in `jawataChat.studio` or `jawataJava.studio` (a command and its args, which the jawata studio's deploy writes), detached so that it keeps running when the editor closes, and asks the address once a second for up to 120 seconds. If the studio setting is missing, the address is missing, the program cannot be started, or the service does not answer in time, the extension says which of these it is in its log and in a notification, and goes on as it did before.

The two studio settings are machine settings: a workspace cannot set them.

### The folders of the window decide the jawata workspace

When the window has folders open and the studio setting carries `handoffDir` (the deploy writes it, next to `args: ["--background"]`), each extension starts the studio with `--editor-folder <folder>` for each folder, every time the window starts and also when the engine's service already answers (a running studio receives the arguments). The two extensions of one window send one launch. The studio answers in `<handoffDir>/<id>.json`, where `<id>` is the SHA-256 of the folders sorted by their bytes and joined with a newline, and the extensions poll it once a second:

- `ready`: the answer's address and key are used for this window only, as `JAWATA_URL` and `JAWATA_KEY` in the environment of the chat's agent and of the Java launcher. They are never written to a setting, a log line or a notification.
- `asking`: the studio's window asks the person whether to update a workspace that matches only some of the folders; the extension says so once and waits for the answer for at most 10 minutes; after that it warns and goes on with the setting's address. The studio removes the old answer file when a launch begins and writes nothing until its resident has answered, so a file that goes away is not an answer: the extension goes on waiting, and the wait for a missing file (330 seconds) starts again from that moment. An answer, or a question, that was already in the file before the launch is distrusted for 3 seconds or until the file changes.
- `declined`, `none`: the engine address in the extension's own setting is used, as before, and the log says why.
- `failed`: a warning with the studio's message, then the setting's address, as before.
- No answer within 330 seconds (the studio gives its own engine 300 seconds to start): a warning, then the setting's address, as before.

A setting without `handoffDir`, or a window without a folder, behaves as described in the previous section.

## Install

Download the `.vsix` files and install them with `code --install-extension <file>`, or with Extensions > Install from VSIX.
